# Landmines

Things in this codebase that look like one thing but ARE another. Each entry exists because someone — usually an LLM agent — read the code wrong, and the wrong read was tempting enough that the next agent would make the same mistake.

**What goes here:** the irreducible-judgment class. Traps that grep, type-check, and "read more carefully" do NOT catch on their own.

**What does NOT go here:** patterns (`.claude/rules/code-patterns.md`), security rules (`.claude/rules/security.md`), testing conventions (`.claude/rules/testing.md`). Landmines are *specific call-outs about specific code*.

---

## L1: RLS is row-level, not column-level — owner-writable policies need a guard trigger for privileged columns

- **Looks like:** `profiles_update_own` (in `supabase/migrations/0002_rls_policies.sql`) — `USING (id = auth.uid()) WITH CHECK (id = auth.uid())` — should be safe: a member can only touch their own row.
- **Actually is:** RLS policies check *which rows* a statement may touch, not *which columns*. Nothing in `profiles_update_own` stops a member from setting `is_admin = true` on their own row in the same `UPDATE`, which grants them `is_admin()` — full read/write over every table including `membership_applications`. Similarly, `profiles_insert_own` originally let a fresh signup insert their own row with `status = 'active'`, bypassing manual admin approval.
- **Why the wrong read is tempting:** "owner can only touch their own row" reads as "owner can only make safe changes to their own row." Those are different claims — RLS enforces the first, not the second.
- **Where exposed:** `supabase/migrations/0002_rls_policies.sql` (the original hole) and `supabase/migrations/0004_profile_privilege_guards.sql` (the fix — `guard_profile_privileges()`, a `BEFORE INSERT OR UPDATE` trigger that pins `is_admin`, `status`, `member_since` to safe values unless `is_admin()` is already true).
- **What to do instead:** any new table with an owner-writable policy AND privileged/gating columns needs a matching `BEFORE INSERT/UPDATE` guard trigger, not just a row-scoped policy. Before shipping a new owner-writable RLS policy, ask "which columns on this row would be bad for the owner to set arbitrarily?" and check whether a trigger protects them. See `.claude/rules/code-patterns.md` § "Supabase RLS Patterns" for the pattern.
- **Caught by:** `0004_profile_privilege_guards.sql`'s own migration comment, which documents both holes it closes.

## L2: Next.js 16 APIs differ from training-data Next.js — read the vendored docs before writing framework code

- **Looks like:** ordinary Next.js App Router code — Route Handlers, `params`/`searchParams`, `cookies()`/`headers()`, caching directives — that you already know from training.
- **Actually is:** `AGENTS.md` at the repo root (auto-generated by `create-next-app`, re-added by `next dev` if removed) explicitly warns: "This is NOT the Next.js you know... APIs, conventions, and file structure may all differ from your training data." Next 16 changed things like async `params`/`searchParams`, caching defaults, and other APIs that plausibly-correct pre-16 code will get subtly wrong.
- **Why the wrong read is tempting:** Next.js App Router patterns feel stable and well-known; the temptation is to write from memory instead of checking.
- **Where exposed:** `AGENTS.md` (repo root); real docs at `node_modules/next/dist/docs/` (resolve the path from the repo root — in a monorepo this could differ, but this repo is flat so `node_modules` is always at root).
- **What to do instead:** before writing any nontrivial framework-facing code (Route Handlers, dynamic params, caching/revalidation, middleware), read the relevant guide under `node_modules/next/dist/docs/`. Heed deprecation notices. Don't assume pre-16 patterns transfer.

## L3: This repo is PUBLIC — `.env*` is gitignored except `.env.example`, and fixtures/seeds must never carry real member PII

- **Looks like:** a normal private-feeling app repo where a stray secret or a real member's phone number in a fixture is an internal-only concern.
- **Actually is:** the repo is public. `.gitignore` excludes all `.env*` files except `.env.example` (verify this holds for any new env-var-carrying file you add — a new `.env.local.backup` or similar pattern needs an explicit gitignore entry, don't assume `.env*` glob catches every naming variant you invent). `src/lib/fixtures.ts` already documents this constraint in its own header comment: member names/cities/cars are founder-approved for the public repo, but phone numbers, emails, and social handles must never be added, to fixtures or to any seed data.
- **Why the wrong read is tempting:** most side-project repos are private; the instinct to relax about what goes in fixtures/seeds/commits doesn't get re-checked against this repo's actual visibility.
- **Where exposed:** `.gitignore` (root), `.env.example` (the only committed env file), `src/lib/fixtures.ts` header comment.
- **What to do instead:** before committing, verify no secret made it into a tracked file (`git status` review, not just `git add -A`). Before adding fixture or seed data, verify it contains no phone numbers, emails, or social handles — even for real, founder-approved member names. If you need to demonstrate a feature that touches PII-shaped fields, use obviously-fake placeholder values, never a real member's actual contact info.

## Adding new entries

Add an entry here when:
- An LLM agent (you or another) misread the code in a way that's likely to repeat.
- A code reviewer caught a "looks like X, is Y" trap.
- You catch yourself thinking "this looks dormant / simple / obviously safe" — write the entry BEFORE proceeding.

Entry must include: name, looks-like, actually-is, why-tempting, where-exposed, what-to-do-instead.
